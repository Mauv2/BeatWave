# BeatWave1 프로젝트 종합 점검 보고서

점검일: 2026-10-06 (한국 시간)  
대상: `C:/unityPrj/BeatWave1` · Unity 2022.3.60f1 · Windows Standalone  
방법: 프로젝트 파일·게임 코드·씬 직렬화·채보·기존 배포 파일 분석, Unity MCP 조회, Stage2 플레이 모드 진입 및 에디터 로그 확인

## 1. 종합 판단

**BeatWave1은 캐릭터가 자동으로 달리는 2D 횡스크롤 리듬 게임이다.** W/S로 위·아래 노트를 처리하고, 지형과 점프, 배경 변화, 고정 화면 이벤트와 동굴 전환을 음악에 결합하려는 구조다. 단순한 노트 판정 화면보다 공간을 이동하는 느낌과 장면 연출이 강점이다.

타이틀 → 곡 선택 → 스테이지 → 결과라는 제품 흐름, 판정·점수·체력, 일시정지와 재시도까지 코드가 존재한다. 다만 **현재 상태는 출시 전 안정화가 필요한 프로토타입**으로 판단한다. 특히 곡 선택 배열 불일치, 스테이지별 채보 연결, 정상 완주 종료 조건, 음악과 이동의 시간 기준이 우선 해결 대상이다. 연출과 기능의 수를 늘리기보다 두 곡의 시작부터 결과까지 일관된 플레이를 보장하는 것이 먼저다.

이 평가는 코드와 설정에 근거한 엔지니어링 판단이다. 실제 재미, 음악과 채보의 체감 품질, 장시간 안정성, 프레임률을 측정한 평가는 아니다.

## 3. 어떤 게임인가

### 플레이 흐름

1. 타이틀에서 Space를 눌러 메뉴를 표시한다.
2. 곡 선택 화면에서 A/D로 카드를 이동하고 Space로 시작한다. 마우스 곡 버튼은 미리듣기와 재선택 시작 기능을 제공한다.
3. 캐릭터가 오른쪽으로 자동 이동한다. 노트는 채보 시간과 이동 속도로 계산한 월드 위치에 미리 배치된다.
4. W는 위쪽, S는 아래쪽 노트를 판정한다. Tap은 누르기, Hold는 유지, Mash는 제한 시간 내 연타다.
5. 점프 트리거와 배경 전환, 고정 화면 이벤트와 낙하 연출을 통해 구간 분위기를 바꾼다.
6. 판정에 따라 점수·콤보가 올라가며 Miss는 체력을 줄인다. 체력 소진 또는 종료 처리로 결과 화면에 이동한다.
7. 결과에서 점수, 판정 개수, 정확도, S~D 랭크를 보고 재시도하거나 타이틀로 돌아간다.

## 4. 가장 먼저 수정해야 할 문제

우선순위는 P0=해당 경로의 진행 차단/배포 차단, P1=핵심 품질과 공정성, P2=유지보수·확장·완성도 기준이다. P0가 모두 현재 실행에서 재현됐다는 의미는 아니다.

| 우선순위 | 문제 | 영향 | 확인 수준 |
|---|---|---|---|
| P0 | 카드 5개, 곡 데이터 4개 | 다섯 번째 카드로 이동하면 인덱스 4 접근으로 예외 발생 경로 | 씬+코드 확정 |

| P2 | Assets 안 대용량 원본 패키지 | 공유·백업·소스 관리 비용 증가 | 파일 크기 확인 |

### 4.1 곡 선택은 먼저 고쳐야 한다

`Select.unity:1749`의 cards는 5개이며 `:1755`의 musicDatas는 4개다. `GameSelectManager.cs:48` 및 `:60`에서는 카드 길이로 인덱스를 순환시키고, `:82`와 `:127`에서는 그 인덱스로 곡 데이터 배열을 읽는다. A로 첫 카드에서 왼쪽 이동하거나 D로 마지막 카드까지 이동하면 `musicDatas[4]`를 참조한다.

Song3Data는 오디오가 있지만 sceneName과 곡명이 비어 있고, Song4Data는 재생 클립과 sceneName이 없다. 마우스 버튼 3개가 Song3Data를 공유하는 반면 키보드 목록의 네 번째 항목은 Song4Data라 입력 방식에 따라 선택 결과도 달라진다.

**보완:** 준비 완료된 두 곡만 노출하고 하나의 곡 목록에서 카드와 버튼을 생성한다. MusicSelectManager와 GameSelectManager의 선택 상태·미리듣기·시작 처리를 통합한다. 미완성 곡은 비활성 상태로 표시하고, 시작 전 곡/클립/씬/채보 유효성을 검사한다.

### 4.2 정상 완주 종료 조건이 현재 구조와 맞지 않는다

`PlayNote.cs:75`의 nNoteCnt는 0으로 초기화된다. 증가시키는 `:190` 코드는 `:90~193`의 블록 주석 안에 있다. 반면 `:196~205`는 여전히 `nNoteCnt >= noteData.Count`를 결과 이동 조건으로 요구한다. 현재 비어 있지 않은 채보에서는 이 조건이 충족되지 않는다. HP 소진과 Z 키의 별도 결과 경로가 있어 이 문제가 가려질 수 있다.

**보완:** 노트 배치를 담당하는 NoteMapPlacer와 판정 처리가 같은 활성 채보를 공유하도록 바꾼다. 종료는 실제 곡 종료·마지막 판정 가능 시간·남은 미처리 노트·연출 상태를 기준으로 한 곳에서 결정한다. 성공/실패/중단을 결과 데이터에 명시하고 종료 후 입력과 점수 변경을 차단한다.

### 4.3 채보 파일과 스테이지 연결이 일관되지 않는다

| 파일 위치 | 노트 수 | 구성 | 마지막 노트 시간 |
|---|---:|---|---:|
| Assets/notedata.json | 92 | Tap 90, Hold 2 | 98.90초 |
| Assets/notedata_Stage2.json | 62 | Tap 60, Hold 2 | 63.15초 |
| Assets/notedata JSON/notedata.json | 31 | Tap 31 | 31.40초 |
| Assets/notedata JSON/notedata_cave.json | 27 | Tap 26, Mash 1 | 27.37초 |
| Assets/notedata JSON/notedata_Stage2.json | 27 | Tap 26, Mash 1 | 27.37초 |
| Build/BeatWave1_Data/notedata.json | 31 | Tap 31 | 31.40초 |
| Build/BeatWave1_Data/notedata_Stage2.json | 27 | Tap 26, Mash 1 | 27.37초 |
| Build/BeatWave1_Data/notedata_cave.json | 27 | Tap 26, Mash 1 | 27.37초 |

모든 JSON 파싱과 현재 검사 항목은 통과했다. 시간순으로 정렬되어 있고 유형·양수 길이/연타 값에 오류는 없었다. 동일 줄의 홀드 시간 안에 다른 노트가 들어가는 패턴도 발견하지 못했다. 이는 음악과 채보가 맞는다는 검증은 아니다.

현재 저장된 Stage1과 Stage2의 일반 NoteMapPlacer는 모두 `notedata.json`을 가리킨다. PlayNote 역시 파일명이 하드코딩돼 같은 파일을 읽는다. 따라서 **62개짜리 Stage2 전용 JSON은 현재 Stage2의 일반 배치 경로에 연결돼 있지 않다.** Stage2 로그에서 92개 중 64개는 생성되고 28개는 지면 검색 실패로 건너뛴 기록이 확인됐다. 씬 설정의 잘못된 채보 연결과 일치하는 증거다.

기존 Build의 파일은 Assets 루트보다 보관 폴더 파일과 해시가 같다. 배포본과 최신 에디터의 콘텐츠 불일치는 확정이지만, 이 차이가 의도된 버전 차이인지는 확인할 수 없다. 기존 실행 파일이 최신 코드인지도 검증하지 않았다.

**보완:** 곡 ID → AudioClip → 채보 → 스테이지 설정을 하나의 데이터 객체로 연결한다. JSON 경로 문자열을 여러 컴포넌트에서 별도 관리하지 않는다. 맵 길이와 모든 노트·홀드 끝의 지면 유효성을 사전 검증하고, 채보 누락을 경고만 남기고 진행하는 대신 개발 단계에서는 오류로 처리한다.

### 4.4 새 빌드가 재현 가능하지 않다

`PlayNote.cs:65~71`, `NoteMapPlacer.cs:59~68`은 Application.dataPath와 파일명을 조합해 File.ReadAllText를 호출한다. 에디터에서는 Assets 폴더를 읽지만 배포에서는 실행 파일 옆 Data 폴더의 원본 JSON이 필요하다. 현재 Build에는 복사된 파일이 있지만, Assets/Editor에서 자동 채보 복사 빌드 후처리는 발견하지 못했다. 따라서 기존 빌드에 파일이 있다는 사실이 새 빌드의 재현성을 보장하지 않는다.

**보완:** 현재 규모에서는 MusicData가 TextAsset 채보를 참조하도록 하는 방식이 단순하다. 외부 JSON이 필요하면 StreamingAssets에 포함하고 로딩 계층을 둔다. 파일 누락·JSON 파싱·필수 필드·문화권별 숫자 변환 실패를 명확히 처리한다. 저장 가능한 사용자 데이터와 채보 제작 파일의 경로도 구분한다. Unity는 StreamingAssets 파일의 원본 포함과 플랫폼별 접근 방법을 문서화하고 있다. [Unity 2022.3 Streaming Assets](https://docs.unity3d.com/2022.3/Documentation/Manual/StreamingAssets.html)

`NoteMove.cs:3`에는 런타임 폴더의 `using UnityEditor;`가 남아 있다. 새 Player 빌드에서 편집기 전용 의존성으로 문제가 생길 수 있으므로 제거/분리 후 빌드를 확인해야 한다. 이번 점검에서 새 빌드를 수행하지 않았으므로 실제 빌드 실패로 단정하지 않는다.

## 5. 리듬 게임으로서의 핵심 품질 위험

### 5.1 음악과 이동이 같은 시간표를 사용하지 않는다

NoteMapPlacer는 `judgeX + createTime * playerSpeed`로 노트를 고정 배치하고 PlayerMove는 FixedUpdate에서 속도 5로 이동한다. JudgeManager는 음악 시간보다 노트와 판정점의 2D 거리를 사용한다. 속도 5와 수평 이동만 가정하면 0.2/0.4/0.6 거리 창은 약 40/80/120ms다. 실제로는 점프와 경사 때문에 Y 거리도 결과에 들어간다.

Mash는 `PlayNote.PauseNoteFlow()`로 플레이어 이동을 멈추지만 AudioSource를 일시정지하지 않는다. 멈춘 시간만큼 공간상의 다음 노트 도착과 음악의 진행이 갈라지는 구조다. 고정 이벤트도 이동을 멈추고 일반 노트를 삭제하는 동안 음악을 계속 재생한다. 최초 시작에서는 오디오를 먼저 재생하고 동기 파일 읽기와 일괄 배치를 수행하여 초기 로딩 비용도 시작 오차로 이어질 수 있다.

**보완:** 곡의 시간을 기준으로 노트 목표 시각과 입력 오차를 계산하고 시각적 월드 위치는 그 시간에서 파생한다. 시작·정지·연출 전환·복귀 시 음악 시간과 논리 시간의 관계를 한 곳에서 관리한다. 오디오 준비를 끝낸 뒤 예약 시작을 사용하면 프레임 의존성을 줄일 수 있다. Unity는 AudioSource.PlayScheduled를 DSP 시간축 기반의 예약 재생으로 설명한다. [Unity 2022.3 PlayScheduled](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/AudioSource.PlayScheduled.html)

러너 연출을 유지하려면 Mash 구간에서 음악도 멈출지, 이동만 정지하되 이후 공간 배치를 재동기화할지 디자인을 먼저 결정해야 한다. 홀드는 시작 판정을 저장하지 않고 끝까지 누르면 항상 Perfect를 주므로 판정 정책도 통일할 필요가 있다.

### 5.2 일시정지와 종료 중에도 입력 경로가 열려 있다

PauseManager는 gameAudio.Pause와 Time.timeScale=0을 사용하지만 JudgeManager/EventNoteJudge에는 전역 Pause 상태를 검사하는 코드가 없다. Update에서 키 입력과 Tap/Mash 성공 판정이 계속 처리될 경로가 남는다. 홀드 중 키를 놓으면 GetKeyUp으로 Miss가 발생할 수도 있다. Z 결과 이동 역시 막지 않는다.

재시도/메뉴 이동에서는 FadeAndLoadScene이 페이드 시작 전에 timeScale을 1로 되돌린다. 이때 음악은 여전히 Pause인데 게임 이동과 판정이 재개될 수 있다. 종료 저장 뒤에도 JudgeManager.Update가 살아 있어 페이드 중 추가 입력과 화면 점수가 결과 스냅샷과 달라질 가능성이 있다. 여러 음악 소스가 있는 구간에서도 PauseManager는 소스 하나만 관리한다.

**보완:** Loading, Countdown, Playing, Paused, Event, Finishing, Result 등의 상태를 공유하고 입력·판정·이동·음악을 상태에 맞춰 함께 제어한다. 메뉴 전환 중에는 게임을 정지한 채 UI 페이드만 독립적으로 재생한다. 복귀는 재생 준비와 짧은 카운트다운을 거쳐 진행한다. timeScale만으로 모든 로직이 정지한다고 가정하면 안 된다. [Unity 2022.3 Time.timeScale](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Time-timeScale.html)

### 5.3 노트 판정의 수명과 동시 입력 관리가 취약하다

JudgePoint는 줄당 currentNote 하나만 가지고 트리거 진입 때마다 교체한다. 홀드가 진행되는 동안 다음 노트가 들어오면 이전 홀드가 참조에서 밀릴 수 있다. JudgeManager의 currentHoldEffect도 두 줄이 공유하는 단일 변수여서 양쪽 홀드가 동시에 진행되는 패턴에는 맞지 않는다. 현재 채보에서 같은 줄 홀드 중첩이 없으므로 이미 발생한 버그로 보고하지 않는다.

**보완:** 줄마다 시간순 후보 큐를 두고 진행 중 홀드를 별도로 관리한다. 노트마다 생성→대기→홀드/연타→성공/실패→반환 상태와 한 번만 판정되는 규칙을 둔다. 판정 성공·실패와 시각 효과의 참조를 분리한다. 현재 Note에는 원래 목표 판정 시간이 없으므로 시간 기반 판정 전환 시 이 정보를 보존해야 한다.

### 5.4 이벤트 시스템이 제품 씬과 일치하지 않는다

Stage1의 CaveEventManager는 music1/music2가 모두 fileID 0이며 caveMusic만 설정돼 있다. 음악 전환 분기는 두 소스가 필요하므로 현재 설정에서 두 번째 곡 재생은 동작하지 않는다. 동굴 NoteMapPlacer도 `notedata.json`을 읽어 일반 채보를 다시 배치한다. `useSecondMusic` 필드는 실제 분기에서 사용되지 않는다.

또한 코드상 두 번째 음악을 먼저 재생한 뒤 낙하·페이드·이동을 마치고 시간 0 기준으로 새 노트를 배치한다. 소스를 연결해도 전환 연출에 걸린 시간만큼 이미 재생한 음악과 새 채보가 어긋날 수 있다.

Stage2는 FixedEventManager, CaveEventManager, FallTransitionEffect, CaveNotePlacer 오브젝트가 비활성이다. 반면 EventTrigger는 활성이고 비활성 FixedEventManager를 참조한다. FixedEventManager.StartFixedEvent는 자신에서 코루틴을 시작하므로 이 트리거 경로는 정상 작동을 보장하지 않는다. 이벤트 판정점·플레이어·noteRoot 참조도 다수 누락됐다. 사용하지 않을 시스템이라면 트리거와 참조까지 정리하고, 사용할 시스템이라면 활성 상태와 필수 참조를 한 번에 검증해야 한다.

EventNoteJudge는 W 또는 S 어느 쪽으로도 성공할 수 있으며 perfectWindow는 선언만 되어 실제 등급 판정에 쓰이지 않는다. 성공/실패는 일반 점수·콤보·HP에 반영되지 않는다. 이는 이벤트가 순수 연출인지 실제 리듬 과제인지 설계가 아직 분리되지 않은 상태다.

**보완:** 이벤트가 시작·끝나는 곡 시각, 새 음악의 시작점, 새 채보의 원점, 점수 반영 정책을 데이터로 정의한다. 실패해도 장면은 계속 진행되는지, HP가 감소하는지, 결과 정확도에 포함되는지 명시한다.

### 5.5 결과의 의미와 개발용 기능을 정리해야 한다

Z로 강제 결과 이동이 제품 코드에 남아 있다. 정확도 분모는 실제 처리된 Perfect+Great+Good+Miss 합계다. 초반 Perfect 몇 개만 처리하고 Z를 누르면 미처리 노트가 제외되어 높은 정확도와 S가 가능하다. 게임오버와 정상 완주를 구분하는 필드도 없으며 최고 기록은 메모리에만 존재한다.

**보완:** 개발 단축키는 에디터/개발 빌드로 제한한다. 정확도, 곡 진행률, 완주 여부를 분리하여 결과가 의미하는 바를 명확히 한다. 실패·중단에는 완주 보상을 주지 않고, 최고 기록·볼륨·보정값·키 설정은 버전이 있는 저장 데이터로 관리한다.

## 6. 안정성·성능·유지보수

### 확정된 정리 대상

- Title.unity의 세 버튼에 같은 해석되지 않는 스크립트 GUID가 남아 있다. 세 컴포넌트 모두 m_Enabled=0이다. 현재 Stage2의 실시간 Missing Script 조회는 0개였으므로 타이틀의 직렬화 문제와 구분해야 한다.
- `MenuBottonTween.cs`의 MonoBehaviour 클래스명은 MenuButtonTween이며, `Camera Test.cs`의 클래스명은 CameraTest다. 이름과 파일명 일치는 프로젝트 정리·컴포넌트 식별 측면에서 개선 대상이다. 이번 점검에서는 이를 컴파일 오류로 판정하지 않았다.
- Application.dataPath에 쓰는 CreateNote는 제작 도구와 런타임 코드가 섞여 있고 StartNote에서 목록 초기화·파일 오류 처리도 없다. 제작 도구를 제품 플레이 경로에서 분리하는 것이 좋다.
- `Assets/Cinzel/presenta.unitypackage` 약 1.03GB와 `Last.unitypackage` 약 515MB가 Assets 안에 있다. 둘만 약 1.55GB다. 원본 백업을 별도 보관하고 에셋 폴더에서 제외하는 것이 공유·버전 관리 비용을 줄인다. 이 파일들이 그대로 Player에 포함된다고 단정하는 것은 아니다.
- 현재 루트에서 `git status`는 Git 저장소가 아니라고 반환했다. 이 폴더의 Git 변경 추적은 확인되지 않았으며 다른 버전 관리의 사용 여부는 조사하지 않았다.

### 성능 위험: 측정 후 결정할 항목

NoteMapPlacer는 시작 때 모든 노트를 Instantiate하고 Raycast한다. 현재 62~92개에서는 반드시 병목이라고 할 수 없지만 곡 수·노트 수가 늘면 로딩 스파이크 가능성이 있다. NoteMove는 노트마다 Update에서 FindObjectOfType을 하고 판정·Miss 경로에서도 전역 검색이 반복된다. 팝업과 파티클도 매번 생성·삭제된다.

먼저 음악 시작 프레임의 배치 비용, 프레임 시간, GC, 파티클 비용을 Profiler로 측정하고 필요하면 참조 캐시·노트/효과 풀·진행 구간만 생성하는 방식으로 바꾼다. 정지 상태·삭제 상태가 풀에 남지 않도록 수명 규칙을 먼저 만든다. 한 번에 모든 시스템을 풀링하는 것은 권하지 않는다.

### 배포·외부 코드

MCP는 현재 로컬 HTTP 설정을 사용하고 프로젝트별 Windows 도구 경로를 전제로 한다. 이는 게임 런타임 기능과 별개인 개발 환경이다. 다른 PC에서 경로와 패키지 설치를 재현할 문서가 필요하다. MCP 패키지 설치 Git 오류는 초기 콘솔에 있었지만 연결 자체는 점검 시작 때 성공했다.

LJR에는 오래된 WWW 기반 통신 예제와 Mac 로컬 파일 URL이 남아 있다. 제품 씬에서 해당 통신 스크립트의 사용은 발견하지 못했으므로 게임이 실제 외부 서버로 통신한다고 판단하지 않는다. 사용하지 않는 데모·라이브러리는 의존성 확인 후 정리할 수 있다.

상용 음악·이미지·폰트·DOTween Pro 등은 출처와 사용 범위를 목록으로 관리할 필요가 있다. 이번 점검은 라이선스 계약이나 권리 상태를 확인하지 않았으며 위반 여부를 판단하지 않는다.

## 7. 보완 방향: 게임의 개성을 살리는 순서

### 1단계 — 두 곡의 완전한 플레이 흐름 확보

목표는 Title에서 Stage1/Stage2를 시작하고 결과·재시도까지 예외 없이 진행하는 것이다.

1. 미완성 곡을 숨기고 카드와 데이터의 개수를 통일한다.
2. 각 스테이지에 음악과 해당 채보를 명시적으로 연결한다.
3. 정상 완주 조건과 게임오버 조건을 통합한다.
4. 채보 포함 방식을 고쳐 깨끗한 출력 폴더에서도 빌드가 재현되도록 한다.
5. Pause/Finishing 상태의 판정 입력을 차단하고 Z 단축키를 제한한다.
6. 지면 누락 노트를 먼저 없앤다. Stage2의 현재 28개 누락은 성능 최적화보다 우선이다.

완료 기준: 두 곡 각각 정상 완주/실패/재시도/선택 화면 복귀가 가능하고, 시작 시 누락 채보·노트·예외가 없다.

### 2단계 — 판정 공정성과 싱크 안정화

하나의 SongClock과 게임 상태를 기준으로 오디오, 노트 시간, 시각 이동, 이벤트를 연결한다. 일반/홀드/연타/이벤트 판정을 같은 결과 구조로 통일한다. 지형과 점프는 캐릭터 연출에 영향을 주되 의도하지 않은 Y 거리로 판정 난도가 변하지 않게 한다.

설정에는 음악/효과음 볼륨, 키 변경, 오디오/입력 보정, 판정 오차 표시를 추가한다. 대표 곡에서 느리거나 빠른 입력이 어느 방향으로 치우치는지 볼 수 있어야 한다. 30/60/120fps, 창 포커스 상실, 연타 구간, 일시정지 복귀 후에도 목표 시각이 유지되는지 확인한다.

완료 기준: 동일 입력 시점의 판정이 프레임률이나 지형 변화에 크게 달라지지 않고 정지/전환 후 시간 오차가 누적되지 않는다.

### 3단계 — 리듬 러너의 읽기 쉬운 화면과 연출

이 게임의 차별점은 두 줄 입력 자체보다 음악을 따라 풍경과 캐릭터가 이동하는 경험이다. 새 노트 유형을 늘리기 전에 위/아래 색뿐 아니라 형태와 위치로 입력을 구분하고, 점프·파티클·배경 변화 중에도 판정점이 읽히게 한다. 첫 곡 초반에 Tap→Hold→Mash를 짧게 소개하는 튜토리얼과 기본 난이도/연습 모드를 마련한다.

고정 화면 이벤트는 곡의 특정 구간과 연결하고, 복귀 전에 다음 입력을 예고한다. 초심자가 연출을 실패로 오해하지 않도록 이벤트 실패의 영향도 화면에서 알려준다. 옵션에서는 강한 Bloom/효과를 줄일 수 있게 한다. 현재 타이틀 Bloom 범위 8~40은 실제 화면에서 가독성을 확인할 대상이다.

완료 기준: 처음 플레이하는 사람이 설명 없이 두 줄과 홀드를 구분하고, 연출 직후 첫 입력을 예상할 수 있다.

### 4단계 — 곡 추가와 배포를 쉽게 만들기

곡별 데이터에 안정적인 ID, 표시명, 미리듣기 구간, 오디오, 채보, 난이도, 스테이지, 보정값을 넣는다. 채보 기록 도구에 재생 위치 이동·수정·검증을 추가한다. 곡 추가 시 씬 여러 곳의 문자열을 바꾸지 않아도 되게 하고, 공유 매니저는 프리팹/공통 초기화 경로로 관리한다.

최고 기록과 클리어 상태 저장, 결과의 전체 곡 진행률, 채보 총 노트 수, 최대 콤보를 추가한다. 온라인 순위나 다중 플랫폼은 이 기반이 안정된 뒤 진행하는 편이 효율적이다.

완료 기준: 데이터 하나를 등록해 새 곡을 노출할 수 있고, 새 PC·새 출력 폴더에서 동일한 콘텐츠를 빌드할 수 있다.
